# Lobby bot and end-game controls

The host can add one bot at a time in the lobby until the room has four seats. The **Add bot** button sends an authenticated `add_bot` WebSocket command. The server checks host authority, lobby phase, capacity, and action ID before creating a tokenless bot seat; every connected human receives the updated lobby. Replaying the same action ID acknowledges the original action without adding another seat. The existing room-creation option for one to three bots and human joins remain available.

After a match starts, the host can select **End game**, then **Confirm end game**. The server applies `domain.ActionEndGame`, advances one revision, and broadcasts `game_ended` followed by `game_completed`. Scores include completed tricks only; an unfinished trick is not awarded. The final state records the ending host, keeps the public trick and each seat's own private hand for reconnect, and derives winners from current scores. Play, next-hand, and another end command are rejected after completion; replay of the accepted end action ID remains idempotent. An active bot search is canceled, and a stale bot move cannot commit. The final screen offers **Return to join**; another match needs a new room code because completed rooms stay terminal until idle cleanup.

The focused Go tests cover host-only and full-room bot addition, duplicate actions, started-game rejection, early end during a trick and between hands, current-score winners, privacy, reconnect, post-game rejection, and pending-bot cancellation. The repeatable `--browser-bot-smoke` mode uses the real UI for lobby add, a scored trick, end confirmation, final-state reload, and return to join. The D1 release gate and D2 deployment path remain in `scripts/test-release.sh` and `scripts/deploy-dev-pi.sh`; the deployed commit and live checks are reported with the rollout.
